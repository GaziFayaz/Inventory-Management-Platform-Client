# Frontend Internationalization (i18n)

This document describes the current i18n setup for the Inventory Management Platform Client and serves as a strict guideline for AI agents and developers working on this codebase.

## 1. Overview
The application currently supports two languages:
- **English (`en`)** - Default
- **Spanish (`es`)**

Language state is persisted in `localStorage` under the key `app-language`. The setup relies on `i18next` and `react-i18next` without any backend language synchronization (frontend-only persistence). 

## 2. Core Architecture & Files

| Concept | File Location | Description |
|---|---|---|
| **Dictionaries** | `src/i18n/locales/en.json`<br>`src/i18n/locales/es.json` | Contains all UI and Error text. Keys mirror each other exactly. We use nested JSON objects (e.g., `auth: { login: "..." }`) rather than flat dotted strings. |
| **i18n Bootstrap** | `src/i18n/index.ts` | Initializes `i18next`, configures Fallback language, and wires up the JSON dictionaries. |
| **Persistence** | `src/providers/LanguageProvider.tsx` | Provides a React Context (`useLanguage()`) and handles synchronizing the `i18next` language to `localStorage` while listening to tab-sync events. |
| **API Errors** | `src/lib/apiError.ts` | Normalizes Axios errors into standard `ApiErrorResponse` shapes and queries i18next to translate backend `errorCode`s into human-readable text. |

## 3. Standard Component Usage

When building or editing UI components (*never hardcode visible text*):
1. Import the hook: `import { useTranslation } from "react-i18next";`
2. Initialize it: `const { t } = useTranslation();`
3. Use the translation key: `<Button>{t("auth.login")}</Button>`
4. **Mandatory**: Whenever you add a new `t('category.key')`, you **MUST** update both `es.json` and `en.json` simultaneously.

## 4. API Error Handling (Crucial!)

Backend errors return a custom JSON payload containing an `errorCode` (e.g., `"auth.blocked"`). The frontend relies on mapping these codes safely using `i18next`.

### The Flow:
1. When a request fails, `useAxiosSecure` or `useAxiosPublic` interceptors catch the error.
2. The interceptor passes the error to `showApiErrorToast(error)` from `src/lib/apiError.ts`.
3. `translateApiError()` looks inside the locale file under the `errors` nested object for the corresponding key (e.g., `t("errors.auth.blocked")`).
4. **Fallback mechanism**: If the key hasn't been localized yet, it falls back to the English backend `message`. If that's unavailable, it uses a generic translated text (`t("errors.error")`).
5. Finally, the interceptors run `return Promise.reject(error)` so local component `catch` blocks still fire correctly.

# 🤖 Instructions for Future AI Agents

When asked to implement new features, pages, or components in this repository, you **MUST** adhere to the following checklist:

### Rule 1: No Hardcoded Strings
All user-facing text (buttons, paragraphs, labels, placeholders, aria-labels, tooltips) must be requested via `t("namespace.key")`. 

### Rule 2: Keep Keys Clean and Nested
Do not use flat keys with dots (e.g., `"nav.home": "Home"`) inside the dictionary files. `i18next`'s default behavior treats dots as object traversal.
**Correct:**
```json
{
  "nav": {
    "home": "Home"
  }
}
```

### Rule 3: Always Update Both Locales
If you add a key to `en.json`, you must add the exact same key hierarchy to `es.json`. Translate the text to Spanish appropriately. 

### Rule 4: Handling New Backend API Errors
If you consume a new endpoint or read the `backend-docs` and notice a new `errorCode` (like `"inventory.not_found"`):
1. Go to `en.json` and `es.json`.
2. Add it under the `errors` block matching the exact dot-notation segments.
`"errors": { "inventory": { "not_found": "Inventory not found." } }`.
Do not bypass the global `useAxiosSecure` error handling by writing your own manual toasts, unless specifically implementing local/inline validation under a form input.

### Rule 5: Keep Interceptor Promises Intact
If you modify `useAxiosSecure.tsx` or `useAxiosPublic.tsx`, **never** omit `return Promise.reject(error)` inside the error handler. Removing it causes downstream React elements to interpret failed HTTP calls as successful, resulting in `undefined` crashes.

### Rule 6: Form Validation
If using `react-hook-form` + `zod`, translation keys should be registered inside the Zod schemas using a custom error map or inline translations (e.g., `.min(1, { message: t("validation.required") })`). *Note: You must instantiate schemas in component render scope if doing inline translation, or utilize an i18next zod resolver.*
